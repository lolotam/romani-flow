# Document drafts and in-form preview

Administrators automatically retain unfinished document metadata on their account, independently for general creation, each fixed employee/company and each existing-document edit. Resume on another device with the same account. A successful document save clears the exact draft revision inside the same transaction as the document write/upload claim. Completed document issue/expiry dates never become defaults for the next new document.

Drafts contain fields only, not attachments or staged-upload IDs. Choose the file again after refreshing/changing devices; the form displays a reattach notice. While the form remains open, PDF/JPEG/PNG preview uses a transient local URL with cleanup. Existing attachments use the authenticated same-origin file route. No external viewer receives file bytes. PDF display depends on the browser; the form offers a local/same-origin open link.

## Editing and conflicts

Writes debounce for 500 ms and the form shows loading/saving/saved/error state. Normal modal close awaits the current save. Requests use keepalive for bounded metadata writes; abrupt browser/process termination cannot guarantee delivery of an unfinished request. Check the saved status before leaving.

Another device changing the same draft causes a conflict instead of silently overwriting. Reopen the form to read the newer version. Late reads cannot replace typed input. Discard affects only this account/context. Tombstone revisions prevent old writes from recreating a discarded/saved draft. No automatic retry follows uncertain write errors.

## API and release

Admin-only, no-store endpoints: GET/PUT/DELETE /api/document-drafts/:scope. Supported scopes: new, employee:<id>, company:<id>, edit:<id>. Account comes from the authenticated session; x-draft-account must match it to reject requests from an old browser identity. PUT accepts revision/values; DELETE accepts revision. Values are field-allowlisted, at most 16 KiB, with bounded strings/date-only dates and validated references. Writes serialize with document mutations/business erase.

Migration 008_document_drafts.sql is additive and must pass the production release/migration gate before deployment. It adds account-owned metadata/revisions and invalidates related drafts on employee/company/document deletion. Business erase clears private draft values and rotates revisions. Full SQLite recovery backups contain these private drafts; business JSON exports do not. Preserve existing private backup permissions. Image rollback must retain the additive tables/triggers; never replace the production DB or drop the tables merely to roll back this feature. The migration rejects the known pre-008 erase transaction at its seed-marker write with `erase_requires_draft_aware_runtime`; that transaction rolls back before its file-deletion loop. Erase is unavailable on that rollback image. Upgrade to a draft-aware release to erase; never bypass the guard. The current handler sets and removes `document_drafts.erase_active` within its own transaction, so no durable authorization remains after commit or rollback. Every post-008 seed-marker insert/update requires transaction-local authorization. The current bootstrap uses a separate document_drafts.bootstrap_active marker within a savepoint and removes it before release, including on previously empty databases.

No WhatsApp/email activation, sending, environment change or production migration is performed by this implementation. File staging remains at document Save. Verification uses isolated SQLite/API, synthetic files, real client state machine and actual component SSR; SSR does not prove native browser PDF rendering.

Closing after a draft failure/conflict offers an explicit confirmation before discarding unsaved local changes; the last server draft remains. A failed document-save CAS keeps prepared metadata and exposes the conflict. Concurrent discard clicks share one operation. Business erase also rotates an epoch for never-written scopes, so an old first-write reference is rejected. Custom entity names are limited to 100 characters consistently in the input, form schema and draft API.

Uploads from draft-enabled forms carry the account/revision reference and stage under the erase coordinator. Stale references fail before file I/O. Custom ministries are resolved inside the document transaction, so a stale draft failure also rolls back their creation. Save & Add Next reloads the post-commit tombstone before accepting the next draft. Save controls wait for draft loading, while Cancel remains available. Proven client-side/API validation failures leave the already-durable draft saved; unknown save outcomes are shown as failed. Legacy notes over 5000 characters receive explicit form validation rather than a hidden draft-only failure.

Save & Add Next replaces the reset baseline with blank document metadata, clears the selected file and shows a fresh file picker; another submission requires an explicit new selection. The new filename becomes the next discard baseline title. A change-file control remains available after selecting a file, and the picker validates only its advertised PDF/JPEG/PNG types. Initial typing does not change the loading status before the first revision arrives. During Discard the fields are disabled and a distinct status is shown. If an already-open control still delivers an edit, it is retained against the new revision rather than silently replaced by the discard response.

## Upload retries and failed cleanup

An open form retains its staged upload after a failed document save. Reuse validates the current account/draft revision and confirms the upload is still pending; a consumed or missing upload is staged again. No file path is accepted from the browser.

Changing the file first abandons any staged upload through admin-only `DELETE /api/files/uploads/:uploadId`, carrying the current draft reference. Only the account and draft scope recorded at upload may abandon it; stale references are rejected. The client keeps its current selection if the request fails. The server revokes the pending claim under the coordinator before unlink, and retains upload identity/owner in the cleanup queue if deletion fails. A warning reports pending cleanup; retry is idempotent and cannot delete a claimed document attachment. Unstaged local selections can be changed without a server request.

The employee-profile Add Document buttons open the same in-dialog PDF/JPEG/PNG picker and preview used by the general form. Save remains unavailable until a file is selected; the selected file can be changed in place. Local, unstaged selections remain changeable after draft errors. Draft-owned upload validation and all document claim paths enforce their stored account/scope binding; legacy uploads without a draft binding retain their existing behavior.

Migration 008 also adds upload_cleanup_queue. Staging records the generated path there before disk I/O, retaining cleanup responsibility for partial-write failures as well as failed pending-upload registration. Successful pending-upload registration removes that temporary cleanup entry. A cleanup pass removes tracking only after the file is removed or confirmed absent; failed removals remain retryable. Attachment replacement and detach share the same coordinator, so they cannot claim an upload during purge. DocumentService.purgeStaleUploads is asynchronous and returns the number of files removed, including queued rollback work. The release does not claim an automatically scheduled cleanup pass.

Business erase includes queued paths as well as normal attachments. Its response exposes filesPendingCleanup: zero confirms no tracked removal is outstanding; a positive count means file cleanup needs retry, even though business rows have been erased. Tracking survives a failed unlink, including queue-only uploads.
