## Inspection and proposed rollout

Current main workflow has an independent serial Node job and browser matrix capped at one. Browser jobs already start without waiting for Node; preserve that. Serialize only actual prerequisites: npm ci before each shard, browser install before browser runners, built runner retains its existing own build behavior. Node suites import source through tsx; isolated API imports server/app.ts and uses synthetic SQLite/temporary storage, so it does not need a prior production build. Split Node into quality/build, extraction/config/forms, and service/API jobs, each on a separate runner with full checkout history and lockfile install. Build runs first in the quality shard after npm ci. Preserve every named npm suite exactly once and all Chromium/Firefox dev/built/layout commands. A node-gates aggregate always checks the matrix result and refuses failed, cancelled or skipped prerequisites. Browser checks remain mandatory alongside node-gates; no blanket approval of this PR or automatic merge.

Browser max-parallel becomes two; these are separate GitHub-hosted runners, not two browsers sharing one host. Read-only free/df capacity snapshots are added. No observed memory-pressure baseline exists; do not claim its absence. Extra installs/runner startup can raise aggregate cost even if wall time falls.

Docker shared-stage/parallel-build optimization: not applicable to this workflow (no Docker jobs, one build/runtime Dockerfile pipeline). No staging image check exists here, so no main-only relocation is proposed. Main-only would remove pre-merge container coverage if introduced elsewhere; requires separate evaluation and approval. Existing deployment controls untouched.
